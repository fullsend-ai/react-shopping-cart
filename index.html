The feature · TSTAPP-8

An in-page order summary at checkout instead of a browser alert

The storefront is fullsend-ai/react-shopping-cart, a small React demo store whose work is tracked as Stories in the Jira project TSTAPP. Its checkout button opened a browser alert() showing only the subtotal. The ask was a real review step before the order.

The run

Four videos, one line

Each station has an agent with one job. Between stations sit gates, where a person reads the work and decides. Watch them in order.

  1. ST1 Intake · rfe-creator · work type: react-shopping-cart

    1 · The requirement: what the shopper needs

    rfe-creator turned the business ask into a TSTAPP Story and scored it against the storefront's rubric.

    It did not wave the Story through. It flagged it for human attention: summary lines were missing color and style, and the thank-you copy claimed the order was being prepared, which this store does not do.

    Gate. A product manager gave the feature input and answered the open questions before the Story moved on.

  2. ST2 Solution · strat-creator · work type: react-shopping-cart-strategy

    2 · The strategy: how to build it

    strat-creator wrote the engineering strategy into the same Jira Story, grounded in the storefront's own docs/architecture.

    • Refined with the PM's answers from the first gate.
    • Scored 8/8 across feasibility, testability, scope and architecture.
    • Four specialist reviewers (feasibility, testability, scope, architecture) each wrote detailed feedback.
  3. ST2 Solution gate · software engineer · review and push

    3 · A software engineer shapes the plan and pushes it

    A software engineer read the reviewers' feedback and folded it into the strategy: focus handling when the summary opens, resetting the view, and the tests that prove both. Then they pushed the strategy back to the Story.

    Gate. Reviewers advise. The software engineer decides what goes into the plan.

  4. ST4 Code & Review · ST5 Build & Verify · triggered by /fs-code

    4 · The code: a reviewed pull request

    A person typed /fs-code on the Story. That comment is the sign-off. fullsend's agents took it from there in the storefront repo:

    • Code read the requirement and strategy and opened PR #109.
    • Review checked it and posted four findings.
    • Fix resolved all four in one iteration, including updating the architecture docs and tightening the cart tests.
    • Review ran again and approved. 141/141 tests and the typecheck pass, and it runs locally.
    fullsend-ai-coder fullsend-ai-review

    Gate. A human approved the PR too. Merging stays a human call.

How a new product plugged in

Pluggable work types

rfe-creator and strat-creator are stations. Each does one job, and they share one configuration vocabulary. A work type tells a station how to do that job for a particular product. It is a descriptor, types/<type>/type.yaml, that binds the station to:

  • trackerwhere the work lives (here, Stories in TSTAPP)
  • intake gatewhich items the station picks up, and when
  • rubricwhat "ready to move on" means for this product
  • templatesthe shape of the requirement or strategy it writes
  • architecture contextthe docs it reasons from (here, the store's docs/architecture)

The React storefront joined the pipeline by adding two work types. Nobody forked the pipeline or changed the stations' core.

# types/<type>/type.yaml  (simplified sketch)
station:    strat-creator
tracker:    jira · TSTAPP Story
intake:     approved requirement on the Story
rubric:     feasibility · testability
            scope · architecture
templates:  strategy section in the Story
context:    docs/architecture

Why fullsend

Humans decide. Agents do the work.

Gates are the point

The pipeline stops where judgment matters: open questions on a requirement, the final shape of a strategy, the go-ahead to write code, the merge.

Every step is reviewable

Requirements, scores, reviewer feedback and strategies land in Jira. Code lands as a GitHub pull request with tests and an agent review.

Grounded in your code

Strategies are checked against the product's own architecture docs, so the plan fits the codebase it targets.

New products plug in

A work type adapts a station to a new tracker, rubric and architecture. The pipeline stays shared.

Put fullsend on your repos

fullsend is open source. It deploys purpose-built agents on GitHub and GitLab that triage, code, review, fix and learn from every run, with your team at the gates.
